## Goal

A real Company1 employee, on the production tenant host, gets in, gets an answer they are allowed to see, and can tell us when it is wrong — and when something breaks at 09:00 on day two there is a written path from their report to a decision. Concretely: four runbooks (onboarding, support and escalation, the pilot-feedback→eval loop, first-week observation), one rehearsal on staging tenants, and a **list of owner-only steps with a name against each**, so the gate week does not discover that nobody holds an account, that no invite email actually sends, or that no reviewer exists to approve the cases §14.1 needs.

**What this packet never does:** invite a real user, create a real membership, or provision a production tenant. Those need accounts, secrets and a Company1 decision list (§20.8), and AGENTS §6 bars an agent from production resources and credentials.

- a rehearsal script **only** as a thin wrapper that calls T-304's `provision_tenant_v1` and T-201's invite path against staging; no second provisioning or invite implementation, ever (plan §13: one durable mechanism per workflow).

## Must not edit

`src/platform/identity/`, `src/platform/tenancy/`, `src/app/` pages and `src/components/` — this packet **uses** them; a defect it finds is an issue for the owning packet ([FAQ-0007](../FAQ.md)). No second invite path, no second provisioning script, no hand-run SQL that creates memberships (memberships come from a reviewed control-plane action, and §11's F05 line is explicit: no operational access granted to a platform admin). Also out: merged migrations, `src/contracts/`, non-synthetic rows in `supabase/seed.sql` (AGENTS §4.7), production anything (§20.8, AGENTS §6), and other packets' acceptance boxes.

**Data rule for every runbook:** no pilot user's name, email address or role list in this repository; no client document title, site identifier or project code. Placeholders only — the staging fixtures are the existing synthetic identities (`owner1@company1.test`, `field2@company1.test`, `owner2@company2.test` in [supabase/seed.sql](../../supabase/seed.sql)); the real roster stays with the owner. That is AGENTS §4.7 and the §6.2 propagation rule applied to operational documents, and it is why a runbook says "the roster is in the owner's password manager" instead of recording a single address.

## Contract

Consumes, changes nothing: the session and membership rules ([docs/contracts/tenancy-and-context.md](../contracts/tenancy-and-context.md) and FAQ-0011 — the tenant comes from the verified host plus the user's current membership, never from a body, header, cookie value or model output), the chat protocol ([docs/contracts/chat-protocol.md](../contracts/chat-protocol.md)), the knowledge-submission lifecycle (F15 through [T-302b](./T-302b-knowledge-submissions.md): chat text never automatically becomes company fact), and the eval-case contract as [#84](https://github.com/TerraOI/TerraOI/issues/84) and ADR-0010 fix it in T-312. If onboarding exposes a real gap — an invite that cannot be re-sent, a member who cannot reset, a project the pilot needs with no RPC behind it — the packet opens `needs-contract` and records the gap; it never patches another lane's file.

## Acceptance tests (write first)

- [ ] positive: the staging onboarding rehearsal — provision a **third synthetic tenant** (working host `company3-staging.terraoi.app`, added to `wrangler.jsonc` `env.staging.routes` and to DNS **together**, the pairing T-004 records), give it two roles and one project, invite both synthetic users through T-201's path, sign in on that exact host, and show its chat answering from its own corpus while refusing the other tenant's — the two-tenant isolation smoke §20.3 puts at the end of week 1, re-run here because the tree has moved since.
- [ ] positive: every runbook carries an owner-step table with a named blocker per row, and the register row cites the rehearsal's CI job ids and the two staging hosts.
- [ ] positive: the feedback-loop rehearsal — one "Suggest correction" on staging produces a `draft` case carrying a source locator, and the next F35 run ignores it until an eligible reviewer approves (the #102 rule asserted at row level, not in prose).
- [ ] negative: nothing in the diff contains a real email address, a person's name, a client project code, a document title or any credential — `secrets` CI green, and the same rule that removed the quoted payloads in #114 applied to the runbooks.
- [ ] negative: an invited-but-not-yet-active membership and a `removed` one both reach only the generic no-access page (F02: identity proves *who*, membership decides *whether*) — asserted on the staging tenant, and reported as **not run** while `src/app/(tenant)/` does not exist on `main`.
- [ ] negative: the platform admin who provisioned the tenant resolves **no** tenant context and reads no tenant data — T-304's negative re-run at onboarding time, because this is the moment an operator is tempted to grant themselves access.
- [ ] failure: a bounced invite, a link replayed on the wrong host, and a second invite while one is outstanding each end in a stated, non-leaking outcome; a killed provider or a suspended tenant mid-pilot shows the employee the right message, and the runbook's escalation matches what actually happened.

## Assumed, decision owed

- **Whether real users may be invited before the M1-PILOT sign-off.** §15.2 makes M1-PILOT "the first gate real employees pass through", so the assumption here is **no**: the rehearsal is synthetic-only and the first real invite is the owner's act after the gate row is written. A soft pre-gate pilot on staging with named Company1 testers would be a recorded deviation from §15.2 and needs its own approval — **D-11** in [BACKLOG.md](https://github.com/TerraOI/TerraOI/pull/190) (D-8 is whether the gate itself is a packet).
- **Who is on support, and for how many hours.** §17.1 gives mechanisms, not people; the runbook can only name roles ("the on-call builder", "the owner, for any switch flip") until the owner names them.
- **How pilot users are referenced in the repository.** Proposed: opaque roster ids (`P-01`…), the mapping held outside git — because every file here is readable by both lanes' agents, and AGENTS §4.7 protects client data, not only client documents.
