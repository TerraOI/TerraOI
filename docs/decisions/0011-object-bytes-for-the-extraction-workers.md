# ADR-0011 Object bytes for the extraction workers

Status: **accepted** · Date: 2026-11-09 · Deciders: supervisor ([#146](https://github.com/TerraOI/TerraOI/issues/146)), Lane 2 (implementation)
Plan refs: §7.2 (extraction executors, line 386; steps 2–3), §7.3 (private storage), §12.4 (clearance), §13 (the local box, lines 824–831), §20.8 (human steps); F09, F10, F12, F32
Related: [ADR-0005](0005-ocr-job-api-and-artifact-home.md) (the job API, the lease, the artifact home), [ADR-0002](0002-pilot-inquiry-intake.md) §4 (hash-only storage discipline), [ADR-0007](0007-e1-embedding-clearance.md) (what a clearance widening looks like on the record)

## Context

An extractor needs bytes, and nothing merged has a legal way to hand them over:

- The payload contract forbids it. `IngestionJobPayload` is `.strict()` and its doc comment says object access "comes from a short-lived signed URL issued by the job API, never from this message" ([`src/contracts/ingestion-job.ts:13-17`](../../src/contracts/ingestion-job.ts)), and the rules file repeats it ([`docs/contracts/knowledge-and-jobs.md:33-34`](../contracts/knowledge-and-jobs.md)).
- The port has only a read. `ObjectStore` exposes `readBounded` and nothing that mints a URL ([`src/platform/knowledge/object-store.ts:19-21`](../../src/platform/knowledge/object-store.ts)), and the storage adapter itself is a typed unavailable refusal ([`src/platform/knowledge/upload-adapters.ts:19-21`](../../src/platform/knowledge/upload-adapters.ts)). So the merged tree has no byte path to a worker at all — the honest interim state ADR-0005 Consequences names.
- #38 ruled the capture side: private Supabase Storage, the **user's own** token minting the upload URL, and explicitly **no service-role key** in that path. A worker or a box has no user token (plan §13 line 829: no database credentials or service-role keys on the box), so the read side needs a different, named grant rather than a reuse of the capture one.
- The consumer set is two, not one: the bounded cloud worker inside our own deployment, and the tenant's local box, which runs **no inbound listener** and polls the job API (F32).

## Decision

1. **One place, one call.** A Supabase service-role key exists as a `wrangler secret` on the deployment that performs extraction, and it is used for exactly one call: `createSignedUrl(bucket, key, 60)` for the object of the job the caller currently holds a lease on. It never appears in `localbox/`, in `src/app/`, in a test fixture, or in a log line (AGENTS §4.6).
2. **SQL supplies the key, under the lease compare.** `job_api.object_ref_for_lease_v1(p_token_hash, p_job_id, p_lease_token, p_fence)` returns the `object_ref` of the version the **job row** points at. It carries the same arms as every mutating job-API call — tenant and executor from `worker_credentials` with `revoked_at is null`, the `lease_token`, the `lease_fence`, `status in ('leased','running')`, and `lease_expires_at > now()` — and refuses a parent version in `revoked / deleting / deleted` (the filter `knowledge_core.sql:471` already uses) and any executor the version's class does not clear (ADR-0005 §8). The object-locator group in pgTAP `045` pins those refusals by name: a live lease yes, an expired lease
no, a stale fence no, another tenant's job no, a revoked credential no.
3. **A 60-second URL, handed over once.** The signature TTL is shorter than the shortest lease this API issues (60 s minimum, `job_api.max_lease_seconds()` = 1800), so a URL cannot outlive the lease that produced it. It is returned to the lease holder, never stored in `source_versions.payload`, never in an artifact's `notes`, never in an `outbox_events` row, and never logged — the same discipline as the credential digest in `job_api.worker_credentials`.
4. **The containment is the boundary plus the privileges, and the residual is stated.** An import-boundary test (T-211 PR-2, named by the packet) fails if anything outside `workers/` references the signing module. the privilege assertions in `045` pin that `service_role` holds no `insert` on `extraction_artifacts` and no `update` on `ingestion_jobs`, so the same key aimed at the Data API cannot write the pipeline. And a signed URL is useless next to an object key: the bucket is private (#38), and `object_ref` is only visible through RLS to members who may read that version.
5. **The box still receives no secret.** The box calls the job API over the tunnel and receives the URL, then does a plain HTTPS GET for the bytes. It holds one worker credential — a value whose **hash** is what the compares match on (`scripts/worker-credential.mjs`, ADR-0002 §4 discipline) — and no storage key and no database credential (plan §13).

## Consequences

- **This is the widest credential in the system after the dashboard, and that is the honest description.** A leaked service-role key can mint a signed URL for *any* object in the project and can read Postgres with RLS bypass. Two things bound it: the SQL revokes in the same migration that creates the job API (`20261109230000_ocr_job_leases.sql`, on `ingestion_jobs` and every table the job path adds, following `20261105210000_intake_service_role.sql:6-8`), and the key never leaves the one deployment. What does **not** bound it, stated rather than glossed: nothing in this decision stops that key minting a URL for another tenant's object *if the attacker also knows the object key*. `object_ref` is `knowledge/<org>/<source>/v<version>` with uuid components, so it is not enumerable through the API — but uuid-guessability is not a security boundary. The follow-up that would make it one — per-tenant buckets, or a storage policy keyed on the lease — is a supervisor decision on the Storage side, and this ADR names it instead of pretending the current shape closes it.
- **A new secret is a human step, not a repository change.** Binding it, and the `JOB_DB` Hyperdrive pairing ADR-0005 §6 needs, are T-004 §20.8 owner actions; until they exist the worker surface is unreachable and the staging evidence in T-211's packet cannot be produced. `supabase/config.toml:13` is only the local truth about which schemas are exposed, so the dashboard check ADR-0005 §9 asks for still applies.
- **No contract change.** `IngestionJobPayload` stays key-free, so no `src/contracts/` edit and no `database.types.ts` regeneration decision here beyond what the migration itself implies (FAQ-0009).
- **No dependency added by this ADR.** The client that signs the URL (Supabase Storage) is a dependency **PR-2** must list with its reason (AGENTS §6); PR-1 ships SQL, pgTAP and the owner script only.
- **One open topology question, answered by the amendment at the end of this file.** The box reaches the app Worker at `src/app/api/jobs/` (FAQ-0005); the signing key stays on the `workers/` deployment, and that Worker reaches the mint through a Cloudflare service binding to it. Ruled on [#152](https://github.com/TerraOI/TerraOI/issues/152) while #149 and #158 sat open, so PR-2 does not choose: both halves keep the key off the box and the mint under the lease compare, and ADR-0005 §9's tunnel/access human step is where the shape is recorded.

## Alternatives considered

- **A storage credential on the box.** Rejected by #38 and plan §13 line 829: a long-lived key on a machine inside a customer's network is the worst copy in the system, and it cannot be revoked per job.
- **Proxying the bytes through the job API.** Rejected: a 20 MB scan streamed through a request handler turns the job API into a file server, spends Worker memory on document bytes it never looks at, and buys no enforcement the lease compare does not already provide.
- **Putting `object_ref` in the job payload.** Rejected: the payload is a queue message that outlives leases and retries, and the contract forbids it (`ingestion-job.ts:13-17`). A key in the message also cannot be revoked when the lease expires.
- **A per-tenant storage token or bucket policy.** Not rejected on the merits — deferred, and named above as the follow-up decision that would make the leaked-key residual a closed question rather than a bounded one.
- **Reusing the user's own token for the read** (the #38 capture shape). Rejected for this path: the worker has no employee session, and minting one for a machine is the ADR-0005 §3 Option 1 cost the supervisor did not choose.

## Amendment (2026-11-11, [#152](https://github.com/TerraOI/TerraOI/issues/152)): the byte path is its own policy, and the deployment is named

Recorded ruling, not a new decision: both questions below were raised by #149 and answered by the supervisor on #152 while #149 and #158 sat open. Nothing here is a builder's inference, and nothing else in this ADR changes — the containment of Decision 1, the lease compare of Decision 2, the 60-second hand-over of Decision 3, the stated residual of Decision 4 and the no-secret-on-the-box rule of Decision 5 all stand.

**1. Which compute path may read object bytes and write parse output is a policy of its own.** Decision 3's phrase "minted only for an executor the version's class clears" means **this** policy, not [ADR-0005 §8](0005-ocr-job-api-and-artifact-home.md)'s / plan §12.4's model-clearance matrix: that matrix lists model *providers*, and TerraOI's own bounded Worker is not one. Plan §7.2 line 386 routes extraction by document **type**, with no class condition attached.

| Class | `cloud_worker` reads bytes, writes artifacts | `local_box` | Third-party OCR or extraction service |
|---|---|---|---|
| `public` | yes | yes | no route exists in M1 |
| `internal` | yes | yes | no route exists in M1 |
| `client_confidential` | yes | yes | no route exists in M1 |
| `restricted` | never ingested (capture refuses it) | — | — |

- It stays one named function, `job_api.executor_clears_class(executor, class)`, in the same migration: the ruled arm is `p_class in ('public', 'internal', 'client_confidential')` for **both** executors; `restricted` clears nothing for anyone, and an executor the function does not name clears nothing.
- pgTAP `045` pins it: both executors clear `client_confidential` (113-114), neither clears `restricted` (134), an unknown or null executor clears nothing (135), and a cloud lease on a `client_confidential` extract job is handed the object key (136-137) and may write the artifact set (139). The four refusals of Decision 2 — another tenant's job, an expired lease, a stale fence, a revoked credential — are unchanged, and the lease compare itself did not move.
- What the model matrix protects stays protected: artifacts and the chunks derived from them carry the class, F31 still refuses Workers AI, DeepSeek and OpenRouter for compose and verify, and embedding stays under [ADR-0007](0007-e1-embedding-clearance.md). **This amendment widens no model route.**
- **Widening this table later is never a code change.** A third-party OCR route — plan §7.2's "named alternative" — needs its own recorded decision first.

**2. The deployment is named, which closes the bullet left open in Consequences.** `workers/` is a **separate Worker deployment** with its own wrangler config (`workers/wrangler.jsonc`, added by T-211 PR-2), and it is the only home of the service-role key. The app Worker's `src/app/api/jobs/` routes (FAQ-0005) stay the box-facing surface, and they reach the signing code **only through a Cloudflare service binding**; the `workers/` Worker exposes no public signing route. T-004 §20.8 carries the second deploy target and its secret path so nobody adds the key to the app Worker. The consequence for the pull loops: the box's client speaks `/api/jobs/*` on the platform, and the short-lived URL it is handed is minted by the other deployment — and no code in `localbox/` can reach Storage, which is what `workers/import-boundary.test.ts` keeps machine-checked.
